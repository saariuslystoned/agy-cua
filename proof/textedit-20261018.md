## Findings and narrow repair

**Proved:** A real TextEdit text area exposed `AXShowMenu`, and the installed
controller advertised it as clickable. Its deterministic click reached Driver's
`AXPress` route and failed with OS error `-25206`. The controller recorded
`dispatch_failed`, `outcome_unknown`, one uncertain side effect and a halted
session. It did not replay that action.

The candidate change requires actual press support for a text control with an
explicit nonempty action list. It retains `set_value`/`type_text`, existing legacy
handling of absent action metadata, and pressable controls. The added regression
test failed on the original implementation and passes with the change. This
candidate was **not installed or live-qualified**.

**Proved:** In all four recipe-2 attempts, the model opened a new document and
addressed that new window in its guarded Format-menu request. The independent
post-run AX reads show a ruler and Bold formatting controls; the window screenshots
show an empty rich-text document. Yet `invoke_menu` could not find “Make Plain
Text” and listed “Make Rich Text” in the available Format menu. Every controller
halted after this error. Both the new-window identity and the visual/AX evidence
were checked independently of the model's answer.

**Inference, not established root cause:** The app-wide menu appears to reflect
a different document's formatting state. The initial explanation that the newly
created document was already plain text was rejected by its screenshot and AX
controls. No foreground workaround or raw-input replay was attempted.

The next narrow improvement is to prove that Driver menu resolution uses the
requested document's context with a real plain-text/rich-text sibling pair, or
refuses when it cannot do so. Driver behavior belongs upstream. Distinguishing
a proven pre-dispatch menu miss from an uncertain side effect also needs explicit
authority before permitting recovery; this task did not weaken the halt rule.
